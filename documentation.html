Subsidiaries Verification AI

System Architecture, Scraping Methodologies, and Integration Protocols

Abstract This technical specification details the architecture of the Subsidiaries Verification AI, a robust system designed for Legal Entity Mapping (LEM) validation. The document synthesizes the complete operational history of the application, detailing the pipeline from raw Excel ingestion to multi-source Dorking (LinkedIn/Crunchbase), real-time WebSocket telemetry, the Gemini AI fallback matrix, and final structured Excel generation. The overarching heuristic philosophy of the system—"Extreme Benefit of the Doubt"—is also defined.

1. Core Verification Philosophy

The AI operates strictly under the "Extreme Benefit of the Doubt" protocol. During the forensic analysis of a subsidiary relationship, the system assumes the user-provided Excel data is correct. An entity is only marked as NO MATCH if the extracted web evidence definitively proves the entity is a direct competitor or completely unrelated to the Parent Company. Ambiguity defaults to a positive match.

2. System Architecture & Telemetry Flow

The application relies on an asynchronous FastAPI backend to manage web scraping, database caching, and AI inference concurrently. A critical feature of this architecture is the real-time WebSocket telemetry that updates the client UI dynamically.

3. Data Ingestion & Final Output Formatting

Data integrity is paramount. Rather than converting the user's file to a destructive format (like CSV), the system utilizes openpyxl.

  • Ingestion: The backend scans all worksheet names for variations of "LEM" or "legalentitymapping". It then dynamically searches the header row to isolate the target entity column.
  • Output Generation: Once processing concludes, the system modifies the original Excel file directly. Incorrect entities (NO MATCH) are distinctly highlighted in a Light Orange background (Hex: #FFFFD580). Furthermore, the source_link generated by the AI is natively injected using Excel hyperlinking protocols, rendering it clickable within the application without requiring copy-pasting.

4. Web Scraping & Anti-Bot Evasion

A standard Google search is insufficient for rigorous corporate audits. When the user enables the "Deep Corporate Audit" toggle, the system executes specialized evasion techniques to bypass anti-bot firewalls on secure directories.

Parallel Dorking Execution

Directly scraping LinkedIn or Crunchbase is notoriously difficult because they implement massive anti-bot firewalls that block standard scrapers instantly. To bypass this, the backend utilizes "Google Dorking" combined with asyncio.Semaphore buffers to execute three simultaneous queries per entity:

  1. General Search: "{Entity}" "{Parent}" (Captures broad press releases).
  2. LinkedIn Dork: site:linkedin.com/company "{Entity}" "{Parent}" (Forces Google's unfiltered index to bypass LinkedIn's login walls).
  3. Crunchbase Dork: site:crunchbase.com "{Entity}" "{Parent}" (Extracts definitive startup acquisition histories).

The top distinct URLs are aggregated, and Playwright executes an invisible headless browser to extract the pure DOM text, stripping navigation elements via BeautifulSoup4.

5. AI Forensic Engine & Fallback Matrix

The stripped text payloads are fed directly into the Google Gemini AI cluster. The prompt instructs the AI to act as a forensic accountant, reading the Crunchbase and LinkedIn descriptions to definitively prove whether a company was bought out, operates as a subsidiary, or is a competitor.

The Model Fallback Sequence

To ensure absolute fault tolerance against API rate limits and internal server errors, the system implements a strict, cascading fallback hierarchy:

Priority Tier Model Designation Operational Purpose
1 (Primary) gemini-3.6-flash Maximum reasoning capability; default engine.
2 (Secondary) gemini-3.5-flash High-redundancy reasoning fallback.
3 (Tertiary) gemini-3.1-flash Stable legacy fallback.
4 (Safety) gemini-3.5-flash-lite Lightweight, high-throughput model for absolute safety.

6. Interactive Real-Time Ecosystem Graph

To prevent user fatigue during processing, the frontend implements a Vis.js Network Graph. The UI consumes the continuous stream of entity_result WebSocket packets broadcast by the backend. The Parent Company serves as the central focal node. As the AI verifies entities in the background, they instantaneously manifest on the physics-based graph:

  • Verified Matches: Display as solid Green lines.
  • Failed Matches: Display as dashed Red lines.

This graph is entirely interactive, allowing drag-and-drop mechanics and zoom functionality.
