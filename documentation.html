Subsidiaries Verification AI

Comprehensive Architectural Specification and Engineering Whitepaper

Abstract This technical specification details the complete architecture, methodology, and engineering principles behind the Subsidiaries Verification AI. Designed to solve the highly manual, time-consuming enterprise problem of Legal Entity Mapping (LEM) validation, this system fully automates corporate hierarchy verification. The document synthesizes the complete operational history of the application, detailing the pipeline from dynamic non-destructive Excel ingestion, to multi-source Dorking techniques (LinkedIn/Crunchbase), to real-time WebSocket telemetry. It meticulously defines the Generative AI (Gemini) fallback matrix, the physics-based visual frontend, and the overarching heuristic philosophy—"Extreme Benefit of the Doubt"—which governs the system's final determinations.

1. Introduction & Business Problem

In enterprise environments, verifying whether hundreds of legal entities actually belong to a specified parent company is a tedious, labor-intensive task. Traditional audits require human analysts to manually search Google, navigate complex corporate registries, and log evidence in spreadsheets. The Subsidiaries Verification AI replaces hundreds of human hours by orchestrating an intelligent, multi-agent AI framework capable of navigating anti-bot firewalls, extracting structured corporate evidence, and synthesizing deterministic results in seconds.

2. Core Verification Philosophy

The AI operates strictly under the "Extreme Benefit of the Doubt" protocol. During the forensic analysis of a subsidiary relationship, the system inherently assumes the user-provided Excel data is correct. An entity is only marked as NO MATCH if the extracted web evidence definitively proves the entity is a direct competitor or completely unrelated to the Parent Company. Ambiguity or lack of information defaults to a positive match. This minimizes false negatives and ensures minor regional branches without heavy web presence are not incorrectly flagged.

3. System Architecture & Telemetry Flow

The application relies on an asynchronous FastAPI Python backend to manage web scraping, database caching, and AI inference concurrently. A critical feature of this architecture is the real-time WebSocket telemetry that updates the client UI dynamically, completely eliminating the "black box" waiting period common in heavy AI applications.

4. Data Ingestion & Non-Destructive Formatting

Enterprise users rely heavily on custom spreadsheet macros, formulas, and color coding. Rather than converting the user's file to a destructive flat-file format (like CSV), the system utilizes openpyxl.

  • Dynamic Ingestion: The backend scans all worksheet names for variations of "LEM" or "legalentitymapping". It then dynamically searches the header row to isolate the target entity column, allowing the tool to adapt to any template structure without hard-coding column indexes.
  • Non-Destructive Output: Once processing concludes, the system modifies the original Excel file directly in memory. Incorrect entities (NO MATCH) are distinctly highlighted in a Light Orange background (Hex: #FFFFD580).
  • Native Hyperlinking: The source_link generated by the AI is natively injected using Excel hyperlinking protocols, rendering it clickable within the application without requiring users to copy-paste URLs into their browser.

5. The Exact Scanning Procedure & Anti-Bot Tactics

A standard Google search is often insufficient for rigorous corporate audits. When the user enables the "Deep Corporate Audit" toggle, the application executes a highly specific procedural sequence to gather knowledge from the web.

Step-by-Step Procedural Extraction

  1. Query Construction: The system extracts the Parent Name string from the UI and the Entity Name string from the current Excel row.
  2. Parallel "Dorking" API Calls: Instead of directly pinging target websites, the system calls the Serper.dev API (Google Search API) using asyncio.Semaphore buffers to execute three simultaneous, parallel queries per entity:
    • General Search: "{Entity}" "{Parent}" (Captures broad press releases and news articles).
    • Crunchbase Dork: site:crunchbase.com "{Entity}" "{Parent}" (Extracts definitive startup acquisition histories, Series funding details, and holding company portfolios).
  3. JSON Parsing & URL Extraction: The Serper API returns a JSON payload. The procedure iterates through the results array and extracts the link and snippet parameters for the top 5 distinct URLs across all three queries.
  4. Headless Browser Rendering: For each extracted link, the procedure launches an invisible Chromium browser instance via Playwright using page.goto(url). This allows the application to fully render complex, Javascript-heavy web pages that block traditional HTTP requests.
  5. DOM Purification: Once the page is loaded, the raw HTML <body> is captured. The procedure passes this HTML into BeautifulSoup4, which aggressively strips out all <script>, <style>, <nav>, and <footer> tags. The remaining pure semantic text is bundled into an "Evidence String" and passed to the AI Engine.

6. AI Forensic Engine & Fallback Matrix

The purified text payloads are batched (up to 50 entities per batch) and fed directly into the Google Gemini AI cluster. The system prompt instructs the AI to act as a forensic accountant, reading the Crunchbase and LinkedIn descriptions to definitively prove whether a company was bought out, operates as a subsidiary, or is merely a competitor. The AI is strictly constrained to output pure JSON arrays containing boolean match decisions, confidence intervals, and explanatory evidence snippets.

The Model Fallback Sequence

To ensure absolute fault tolerance against API rate limits (HTTP 429) and internal server errors (HTTP 500), the system implements a strict, cascading fallback hierarchy within the google-genai API integration:

Priority Tier Model Designation Operational Purpose
1 (Primary Engine) gemini-3.6-flash Maximum reasoning capability; default execution engine.
2 (Secondary Fallback) gemini-3.5-flash High-redundancy reasoning fallback if Tier 1 is throttled.
3 (Tertiary Fallback) gemini-3.1-flash Stable legacy fallback for high-traffic scenarios.
4 (Final Safety) gemini-3.5-flash-lite Lightweight, high-throughput model guaranteed to execute if heavy models are entirely locked out.

7. Interactive Real-Time Ecosystem Graph

To prevent user fatigue during massive batch processing, the frontend implements a Vis.js Network Graph to visualize the AI's "thought process" in real-time. The UI consumes the continuous stream of entity_result WebSocket packets broadcast by the backend.

  • The Parent Hub: The Parent Company serves as the central focal node (rendered as a distinct, colored block).
  • Verified Matches: As the AI verifies entities, they instantaneously manifest on the physics-based graph, connected to the hub via solid Green lines.
  • Failed Matches: Rejected entities spawn as floating nodes connected via dashed Red lines.

This graph utilizes the barnesHut physics solver to simulate gravitational repulsion, ensuring nodes naturally distribute themselves across the canvas. It is entirely interactive, allowing drag-and-drop mechanics and infinite zoom functionality.

Troubleshooting Note

If the backend server fails to bind during execution, it indicates that port 8000 is already occupied by a hanging Python process. Administrators should utilize netstat -ano | findstr :8000 to isolate the rogue Process ID, followed by taskkill /PID <id> /F to force terminate the process before rebooting Uvicorn.
